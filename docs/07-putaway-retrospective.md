# Putaway 页面改造复盘与回归清单

**更新日期**: 2026-04-15  
**适用范围**: `/putaway` 页面、相关多语言文案、批量上架工作区  
**目标**: 把反复出现的问题沉淀为固定检查项，避免后续再出现“上线后才发现布局炸裂、按钮无效、语言漏翻”的情况。

## 0. 当前已经落地的能力

截至 2026-04-15，`Putaway` 页已经不是只有“选任务 -> 选一个位 -> 确认”这一条老路径了，当前真实能力包括：

### 0.1 更贴近现场的任务入口
- 已支持 3 种任务分组视角：
  - `By handling unit`
  - `By inbound order`
  - `By SKU`
- 这层是入口体验，底层仍然沿用现有 `putaway task` 主线，不会破坏任务、库存和台账。

### 0.2 面向未来 AGV 的执行提示
- 每条任务都已经能显示：
  - `Worker / AGV / Hybrid`
  - `HU`
  - 外部码摘要
  - `Why this route`
- 当前任务摘要区也已明确显示：
  - `Current handoff`
  - `AGV eligible / Worker only`
  - `Why this route`

### 0.3 Split putaway 已经成立
- 前端已经支持：
  - `Split putaway plan`
  - `Add another destination`
  - `Primary final storage location`
- 后端 `putaway confirm` 已支持可选 `allocations`
- 一条 putaway task 可以拆分到多个最终库位
- 如果 allocation 总量不等于任务数量，会明确拦住
- 生产 API 已确认会返回 `allocations` 结果，说明多目的位分配已经不只是本地实现

### 0.4 建议库位更合理
- 建议库位现在会排除当前 `staging/source`
- 不会再把“原地不动”推荐成最终 putaway 目标

## 1. 这轮改造里反复出现的问题

### 1.1 重复模块导致布局冲突
- 典型症状：
  - 右侧出现一整条被挤压成竖条的确认区
  - 左边已经有确认动作，右边还保留旧的 `Execution lane`
- 根因：
  - 新确认区迁移到左栏后，旧确认模块没有彻底移除
  - 页面同时渲染两套“确认执行”逻辑
- 后续规则：
  - 页面每次重构后，先做一次“模块职责盘点”
  - 一个职责只能存在一套主模块

### 1.2 多语言只翻了外壳，核心操作区漏翻
- 典型症状：
  - 菜单和标题是中文
  - 批量工作区、状态词、提示文案仍是英文
- 根因：
  - 新增 UI 时只补了页面标题，没有补深层交互文案
- 后续规则：
  - 每次新增 UI 区块时，必须同时补：
    - 标题
    - 副标题
    - 操作按钮
    - 状态词
    - 空状态
    - 提示文本

### 1.3 批量流程与单条流程分裂
- 典型症状：
  - 单选走一套
  - 多选又跳到另一套界面
  - 用户需要重新理解流程
- 根因：
  - 设计时按“功能堆叠”推进，而不是按“任务闭环”推进
- 后续规则：
  - 先设计统一主路径，再决定单选/多选只是该路径的不同输入规模

### 1.4 规划动作与正式执行没有分层
- 典型症状：
  - 用户分不清“先排位”和“正式上架”
  - 按钮文案语义模糊
- 根因：
  - 规划动作和执行动作都用同等强度按钮并列展示
- 后续规则：
  - 规划动作放在前置步骤
  - 最终执行必须单独做成 `Final confirmation`

### 1.5 真实线上状态没有及时复测
- 典型症状：
  - 代码看起来对了
  - 用户在线上仍看到旧布局或旧文案
- 根因：
  - 改完后只看代码、只跑 build，没有登录生产站复测
- 后续规则：
  - 每次改 `/putaway` 后，必须做一次真实线上复测

## 2. 现在推荐的页面结构

`Putaway` 页建议长期保持为四块：

1. `左栏任务树`
- 按 `handling unit / inbound order / SKU` 切换分组
- 同时支持单条和多条选择

2. `中间图板`
- 用于规划位置
- 支持拖拽和点击

3. `热力图`
- 提供仓库、走道、货架热度参考
- 不承担最终执行

4. `最终确认区`
- 只负责正式执行
- 不再重复展示规划逻辑
- 支持单目的位和 split allocation

## 3. 每次改动后的固定回归清单

### 3.1 布局
- 选中任务后，右侧不能出现被压扁的重复确认栏
- 左栏、中间图板、热力图、确认区职责清楚
- 批量模式下页面不能突然变成另一套结构

### 3.2 功能
- 单选任务可以规划、清除、确认
- 多选任务可以规划、清除、确认
- 单任务可以增加第二个、第三个目的位
- split allocation 总量必须等于任务数量
- 点击一个位置不会重置当前 `区/走道/货架/层`
- 使用系统建议排位后，必须能清除规划并回到手动排位
- 最终确认按钮必须稳定可见
- 建议库位不能等于当前 `staging/source`

### 3.3 多语言
- `zh-Hant / en / es / hu / de` 都检查：
  - 批量状态区
  - 图板提示
  - 按钮文案
  - 状态词
  - 最终确认文案

### 3.4 作业语义
- “规划”与“执行”必须区分
- 每个按钮必须让库管一眼看懂
- `Worker / AGV / Hybrid` 必须是执行提示，不是装饰信息
- `Why this route` 必须说人话，不能露技术判断痕迹
- 不使用模糊表述，如：
  - `Use board result`
  - `Confirm execution path`
- 优先使用直白动作语：
  - `採用系統建議排位`
  - `清除目前規劃`
  - `確認這批正式上架`

## 5. 建议的线上复测路径

1. 登录正式站
2. 打开 `/putaway`
3. 单选一条任务
4. 多选一组任务
5. 手动规划一个位置
6. 使用系统建议排位
7. 清除目前规划
8. 测一次 `split putaway`
9. 确认最终执行按钮可见
10. 切到繁中/西语/德语至少各看一次核心批量区

## 6. 结论

这次改造最大的经验不是“又加了几个功能”，而是：

- 一个页面只能有一套主执行路径
- 每次页面重构都要同时做：
  - 模块去重
  - 多语言补齐
  - 线上真实复测

后续如果继续打磨 `Putaway`、`Receiving`、`Inventory`，都建议沿用这份回归清单。
